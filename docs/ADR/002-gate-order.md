# ADR 0002：为什么检查顺序是功能文档里的 11 步

## 目的

说明为什么不按「合约 → 版本 → 效应 → 预算」的名字顺序做检查。

## 读者

改 `commit.py` 或以为可以重排门的人。

## 范围

只解释 `docs/FEATURES.md` 第 3 节已经定下的顺序。不增加新的门。

## 内容

### 状态

已接受。

### 背景

规格里同时存在合约、预算、效应引用、版本比较和文档约束。若先做版本策略再查预算，一次已经超预算的提交仍可能增加重规划次数，或在不相交合并里把 patch 应用到当前版本上，然后才发现应该 `BUDGET` 并把任务打成 `aborted`。

若在加锁前做版本比较，比较结果在写入前会过期，`same_field` 的后写可能覆盖先写。

### 决定

检查顺序固定为：

1. 结构。任务不存在则 404，不写账本。
2. 任务不是 `running` 则 `TASK_ABORTED`。
3. 幂等。命中则直接返回。
4. 锁住订单行。
5. 路径权限。
6. 预算。失败则 `aborted`，并按补偿规则处理未入账效应。
7. `effect_ids` 必须是本任务已执行的效应。
8. 版本与冲突策略。
9. 在内存副本上应用 patch。
10. 文档约束。
11. 通过才增加版本并写订单、账本、检查点和效应状态。

路径放在预算之前，这样越权不会把任务打成 `aborted`。预算放在版本策略之前，这样超限不会重规划，也不会做不相交合并。效应引用放在合并之前，这样不会把一笔引用了无效效应的 patch 合并进当前版本。文档约束放在应用 patch 之后，因为它看的是结果文档。

插件不能改这个顺序。

### 后果

`contract_only` 只保留结构、路径和文档约束，并仍然写账本。它故意跳过第 6 到第 8 步里的预算、效应去重和版本策略，用来做对照，不是另一套可配置顺序。

对外把这 11 步就叫检查顺序。不用「五道门」这个词。
